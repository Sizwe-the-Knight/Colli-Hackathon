# Session migration review — prepared, not applied

Dependency checkpoint: `70292a4`. The migration is generated by installed
Drizzle Kit 0.31.10 for PostgreSQL 17.11. No database was started or queried.
Existing privileges below are based on prior verified results and
`AUTH_SECURITY.md`; actual grants/default privileges require a future live preflight.

## Prepared objects

`drizzle/0001_persistent_sessions.sql`, its `meta/0001_snapshot.json`, and the
appended journal entry are generated together, without editing generated SQL or
historical snapshots. The migration contains eight statements:

- Create schema `auth`.
- Create `auth.sessions`: `sid varchar` primary key, `sess json NOT NULL`,
  `expire timestamp(6) without time zone NOT NULL`.
- Create `auth.revoked_sessions`: `sid varchar` primary key,
  `revoked_at timestamptz(6) NOT NULL DEFAULT now()`,
  `retain_until timestamptz(6) NOT NULL`.
- Add `users.auth_version integer NOT NULL DEFAULT 1`.
- Add three B-tree indexes: session expiry, `(sess ->> 'userId')`, marker retention.
- Add the positive-auth-version check. Marker creation also includes a check
  requiring `revoked_at < retain_until <= revoked_at + interval '168 hours'`.

Primary keys already index SID lookups; no redundant SID index is needed.
Markers deliberately have no foreign key/cascade to sessions: deleting a session
must not erase its revocation record. The account lookup index uses text without
an integer cast, so malformed legacy JSON does not break index creation or lookup.
It is not a substitute for runtime identity validation.

There are no grants, roles, policies, privileged functions, triggers, telemetry
tables, user deletions or changes to provider selections in this migration.

## Store compatibility and timestamp contract

The installed connect-pg-simple 10.0.0 performs SELECT/UPSERT/UPDATE/DELETE on
`sid`, `sess`, `expire` and uses `to_timestamp(epoch_seconds)` for expiry. The
column types match its shipped table definition, without the obsolete OIDS clause.
Future configuration must explicitly use `schemaName: 'auth'`,
`tableName: 'sessions'`, `createTableIfMissing: false`, and the approved pg Pool.

Because `expire` is timezone-less while `to_timestamp` returns a zoned instant,
all store and expiry-maintenance connections must use and verify UTC. This is a
future integration prerequisite, not a role/database setting changed here.
Marker timestamps are zoned; 168 hours expresses an elapsed seven days without
daylight-saving calendar-day arithmetic. Store expiry rounds to seconds; the
application must independently enforce the exact absolute deadline.

## Approved policy, not activated

- 24-hour inactivity expiry; seven-day absolute lifetime; multiple devices allowed.
- Activity means an accepted authenticated user/API interaction. Merely leaving a
  tab open, loading static assets, health probes and failed authentication do not
  refresh activity. No keepalive polling is proposed.
- Both cookie and persisted expiry are capped by the immutable absolute deadline.
  Stock store touch/TTL behavior alone does not enforce that cap.
- Every protected request checks account existence, matching auth_version, expiry
  and the SID revocation marker. PostgreSQL/store errors fail closed with a
  controlled unavailable response; no MemoryStore production fallback.
- Session JSON contains only identity/security timestamps/version and cookie
  metadata, never passwords, provider credentials or operational telemetry.
- Normal logout revokes only its SID. Revoke-all invalidates all existing sessions
  for that account, including the caller. Successful new login can create a fresh
  session; activity or a stale write cannot promote an old auth_version.

## Adversarial findings and required future controls

1. **Cross-user access:** the backend's shared runtime DB identity can access all
   session rows once granted store privileges. Browser users must never receive
   direct DB access. Derive identity from the validated signed session and stored
   account; reject arbitrary client-supplied account IDs/SIDs as authorization.
   This schema does not provide row-level isolation against a compromised backend.
2. **Fixation/rotation:** retain regeneration and awaited saving at login and
   registration. A replaced SID needs the same late-write protection as logout.
3. **Late writes:** stock store UPSERT can recreate a deleted session. Retain and
   check a separate marker after current-session logout. Version comparison
   invalidates recreated rows after revoke-all. Never update a stale session to
   the current account version merely to make it pass validation.
4. **Revocation races:** protected mutations must revalidate and coordinate their
   account/session locks with revocation. Requests already completed cannot be
   undone. Race tests must define a clear transaction ordering for revoke-all,
   logout, login and provider mutations before runtime activation.
5. **Marker bounds are insufficient alone:** the CHECK prevents indefinite rows,
   but does not prove that retain_until covers the revoked session's remaining
   absolute lifetime. A future trusted revocation operation must derive the
   deadline from validated immutable session metadata; malformed metadata fails
   closed and requires a conservative seven-day marker. It must never shorten an
   existing marker, including under duplicate/concurrent logout requests.
6. **No early deletion:** colli_app must have no direct INSERT, UPDATE, DELETE,
   TRUNCATE, ownership or schema CREATE rights on revoked_sessions. SELECT only
   plus separately approved narrowly scoped operations prevents marker tampering
   through ordinary runtime privileges. Migration owners/superusers inherently
   retain authority; never use their credentials in the application.
7. **Failure handling:** logout/revoke-all must not claim success before the
   marker/version transaction commits. Save/load/touch/cleanup failures must be
   sanitized; no raw session JSON, SQL parameters, SIDs or connection strings in logs.
8. **Existing grants:** colli_app's existing table-level users INSERT would cover
   the new column. Before activation, propose replacing it with explicit INSERT
   columns needed for registration; do not grant auth_version UPDATE. The schema
   also excludes authVersion from insertUserSchema. No grant changes occur here.

## Cleanup and privileged operations — proposal only

Prefer a separate expired-marker cleanup function with no arguments and the fixed
predicate `retain_until <= statement_timestamp()`. Bound each cleanup batch; no
caller-supplied cutoff, SID, table name or dynamic SQL. Return only a count.
Runtime may eventually receive EXECUTE on that operation, never table DELETE.
The function's restricted owner needs the underlying DELETE privilege. Normal
runtime credentials cannot bypass its predicate. No such function or owner is
created in this migration. Until approved, retaining expired markers is safer
than granting unrestricted cleanup access.

A future SECURITY DEFINER design must set a safe search_path (`pg_catalog`, with
`pg_temp` last), fully qualify every application object, revoke PUBLIC EXECUTE in
the creation transaction, and explicitly grant only the approved caller. Its
owner must be a restricted NOLOGIN role provisioned separately; colli_migrator
cannot create roles under its existing restrictions.

Revoke-all and marker-creation operations must independently validate the
persisted caller session, expiry, marker and version and derive its account.
Do not expose an arbitrary target-user function. Validate inside the transaction;
an outer HTTP check alone is vulnerable to revocation races. Shared backend DB
credentials remain trusted; this is least privilege, not protection against total
backend compromise. Account deletion is entirely outside this session's scope.

## Offline verification and repeatable generation

From `C:\Projects\Colli\lib\db`, using the installed binary directly (pnpm exec
shim resolution failed in this Windows environment):

```powershell
node node_modules/drizzle-kit/bin.cjs generate --config ./drizzle.generate.config.ts --name persistent_sessions
node node_modules/drizzle-kit/bin.cjs check --config ./drizzle.generate.config.ts
```

The generation-only config reads no credentials and imports no DB pool. It uses
forward-slash schema paths and a cwd-relative output path to avoid this Drizzle
release's Windows glob/snapshot path problems. The original connection-bearing
config is untouched. These commands generate/check files; they do not apply SQL.

`node --test tests/session-migration.test.mjs` checks the journal chain, preservation
of all original user columns/constraints, exact regenerated SQL, absence of schema
drift, and the intended object/privilege boundary. It uses Drizzle's offline API
and schema definitions only. It is not a PostgreSQL execution or privilege test.
